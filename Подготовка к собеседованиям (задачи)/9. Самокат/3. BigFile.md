**Системная / алгоритмическая задача уровня senior+**
```
Есть некоторый сервер, с большим количеством оперативной (расширяемая, но менее 1 тб) памяти
и с ограниченным жестким диском под  1 файл весом 10тб

Задача: реалзиовать АПИ которое возвращает по id пользователя все его данные из файла

Сам файл имеет вид

111;его_строковые_данные11
232;его_строковые_данные22
323;его_строковые_данные33;
111;его_строковые_данные44;
111;его_строковые_данные55;
111;его_строковые_данные66;

На вход принимаем id пользователя, API должно вернуть (за разумное время на порядки меньше времени чтения всего файла)
его строковые данные

ВХОДНЫЕ ДАННЫЕ
111

ВЫХОДНЫЕ ДАННЫЕ
[ 
   его_строковые_данные11,
   его_строковые_данные44,
   его_строковые_данные55,
   его_строковые_данные66 
]"

O(K), где K это количество выдаваемых строк на запрос
```


## 🔹 Условия (переформулируем чётко)

* Есть **один файл ~10 ТБ**
* Файл **строковый**, формат:

  ```
  user_id;payload
  ```
* Один user_id может встречаться **много раз**
* RAM < 1 ТБ (много, но **меньше файла**)
* Нужно API:

  ```
  get(user_id) -> [payload1, payload2, ...]
  ```
* Время ответа **на порядки меньше**, чем чтение всего файла
* **Сложность запроса: O(K)**, где `K` — количество строк этого пользователя
* Файл **на диске**, диска мало → копию файла делать нельзя


## 🔥 Ключевая идея (коротко)

> **Предварительно построить индекс по файлу**,
> где для каждого `user_id` хранятся **смещения (offset'ы) строк в файле**.

API:

* не читает весь файл
* читает **только нужные куски**
* ровно `K` операций чтения


# 🧠 Архитектура решения (правильная)

## 1️⃣ Одноразовая оффлайн-предобработка (или фоновая)

### Строим индекс:

```
user_id → [offset1, offset2, offset3, ...]
```

Где `offset` — позиция начала строки в файле.

### Как строим:

```python
offset = 0
for line in file:
    user_id, data = parse(line)
    index[user_id].append(offset)
    offset += len(line)
```

## 2️⃣ Где хранить индекс?

### Варианты (по возрастанию масштаба):

| Вариант             | Когда подходит                           |
| ------------------- | ---------------------------------------- |
| RAM (dict)          | если уникальных user_id не слишком много |
| mmap + файл индекса | если индекс большой                      |
| RocksDB / LevelDB   | production-ready                         |
| Redis + persist     | если RAM хватает                         |

💡 **Важно:**
Индекс **на порядки меньше**, чем 10 ТБ
(мы храним числа, не строки)

## 3️⃣ Оценка памяти индекса

Допустим:

* 1 млрд строк
* offset = 8 байт
* user_id = 8 байт
* overhead ≈ 8 байт

➡ ~24 байта на строку\
➡ **24 ГБ индекс на 1 млрд строк**

➡ Реалистично помещается в RAM или KV-хранилище


## 4️⃣ API-запрос (O(K))

### Алгоритм запроса:

1. Получаем список offset'ов по `user_id`
2. Для каждого offset:

   * `seek(offset)`
   * `readline()`
   * извлекаем payload
3. Возвращаем список

### Псевдокод:

```python
def get_user_data(user_id):
    offsets = index.get(user_id, [])
    result = []

    with open("datafile", "r") as f:
        for off in offsets:
            f.seek(off)
            line = f.readline()
            _, payload = line.split(";", 1)
            result.append(payload.strip())

    return result
```

## ⏱ Сложность

| Этап   | Сложность       |
| ------ | --------------- |
| Индекс | O(N) — один раз |
| Запрос | **O(K)**        |
| Память | O(N_offsets)    |

✔ Требование выполнено\
✔ Нет чтения всего файла\
✔ Масштабируемо\
✔ Реалистично для production


# ⚡ ВАЖНЫЕ оптимизации

## 🔹 1. Сортировать offsets

Offsets уже идут по порядку → чтение почти sequential
Минимизируем seek latency

## 🔹 2. mmap вместо seek/read

```python
mmap_file[offset : offset+line_length]
```

* быстрее
* меньше syscalls

## 🔹 3. Хранить offset + length

Чтобы не делать `readline()`:

```text
offset, length
```


## 🔹 4. Кэш горячих пользователей

LRU:

```python
cache[user_id] = result
```


# 🛡 Что если файл обновляется?

### Варианты:

1. **Append-only**

   * обновляем индекс инкрементально

2. **Versioned index**

   * новый файл → новый индекс

3. **Write-Ahead Log**

   * для online-обновлений


# ❌ Плохие идеи (и почему)

| Идея                   | Почему плохо         |
| ---------------------- | -------------------- |
| Читать файл каждый раз | O(N)                 |
| grep                   | линейно              |
| Загружать файл в RAM   | >1 ТБ                |
| Делать 1 файл = 1 user | слишком много файлов |
| JSON                   | гигантский overhead  |

# 🧠 Как это звучит на собеседовании (идеальный ответ)

> Мы не можем читать 10 ТБ файл на каждый запрос.\
> Решение — построить оффлайн индекс: `user_id → offsets`.\
> Индекс хранит позиции строк в файле.\
> API при запросе читает только нужные offsets, обеспечивая O(K) сложность.\
> Это классический inverted index / file offset indexing.\
> Используем mmap или seek + read, индекс храним в RAM или KV-хранилище.


# 🏆 Ключевые термины (важно!)

* Inverted index
* File offset indexing
* mmap
* Random access I/O
* O(K) query
* Append-only log
* Read amplification
