**Классическая ловушка продакшен-багов** в Django/DRF 👇
Подсказка в тексте очень точная: проблема **не** в похожести методов, **не** в POST/PUT и **не** в стиле.
И даже `transaction.atomic` тут **не спасает**.


## 📌 Исходный код (суть)

```python
@api_view(['POST'])
@transaction.atomic
def api_increase_a(request, investor_id):
    investor = get_object_or_404(Investor, pk=investor_id)
    investor.a += 100
    time.sleep(0.5)
    investor.save()
    return Response({"status": "OK"})


@api_view(['POST'])
@transaction.atomic
def api_increase_b(request, investor_id):
    investor = get_object_or_404(Investor, pk=investor_id)
    investor.b += 100
    time.sleep(0.5)
    investor.save()
    return Response({"status": "OK"})
```

# 🚨 Главная проблема: **Race Condition (состояние гонки)**

Это классическая проблема **lost update** (потерянное обновление).

## Что происходит:

### Сценарий:

Пусть `a = 0`, `b = 0`

Два запроса одновременно:

* Запрос 1 → `api_increase_a`
* Запрос 2 → `api_increase_b`

### Хронология:

1. Оба запроса делают:

```python
investor = get_object_or_404(...)
```

➡ оба получают **ОДНУ И ТУ ЖЕ версию объекта из БД**
например: `a=0, b=0`

2. Первый:

```python
investor.a += 100   # a=100, b=0
```

3. Второй:

```python
investor.b += 100   # a=0, b=100
```

4. Первый делает:

```python
investor.save()
```

В БД теперь:

```
a=100, b=0
```

5. Второй делает:

```python
investor.save()
```

⚠ Он сохраняет **СВОЮ копию объекта**, где:

```
a=0, b=100
```

➡ В БД становится:

```
a=0, b=100
```

❌ **Результат:** изменение `a` потеряно
Это и есть **lost update**


# ❗ Почему `transaction.atomic` НЕ спасает?

Потому что:

* `atomic` гарантирует **целостность транзакции**
* но **НЕ сериализацию конкурентного доступа**
* оба запроса работают с **устаревшими snapshot-данными**

Это не проблема транзакции — это проблема **изоляции и конкурентного доступа**

# 🧠 Тип проблемы:

**Race Condition / Lost Update / Dirty Write**

# ✅ Правильное решение

Нужно использовать **атомарные обновления на уровне БД**, а не через Python-объект.

## Вариант 1 — через `F()` выражения (правильный продакшен-подход)

```python
from django.db.models import F

@api_view(['POST'])
@transaction.atomic
def api_increase_a(request, investor_id):
    Investor.objects.filter(pk=investor_id).update(a=F('a') + 100)
    return Response({"status": "OK"})


@api_view(['POST'])
@transaction.atomic
def api_increase_b(request, investor_id):
    Investor.objects.filter(pk=investor_id).update(b=F('b') + 100)
    return Response({"status": "OK"})
```

### Что происходит теперь:

SQL будет вида:

```sql
UPDATE investor SET a = a + 100 WHERE id = ...
```

И

```sql
UPDATE investor SET b = b + 100 WHERE id = ...
```

✅ БД сама гарантирует атомарность
✅ Нет чтения старого состояния
✅ Нет lost update
✅ Нет race condition
✅ Потокобезопасно
✅ Процессобезопасно
✅ Работает в распределённых системах


# 🛡 Альтернатива (хуже, но иногда нужна)

### `select_for_update()` (row-level locking)

```python
investor = Investor.objects.select_for_update().get(pk=investor_id)
```

➡ блокирует строку в БД до конца транзакции

❌ плохо масштабируется
❌ создаёт блокировки
❌ может приводить к дедлокам
✔ но предотвращает race condition

# 🎯 Правильная архитектурная мысль:

> Никогда не делай `obj.field += 1` + `save()`
> в конкурентной среде для счётчиков/балансов/статистик

Это **антипаттерн** для веба.


# 💬 Как это формулируют на собеседованиях:

* race condition
* lost update
* non-atomic update
* stale object update
* read-modify-write problem
* concurrency bug

# 🧠 Идеальная формулировка ответа:

> Проблема в read-modify-write паттерне.
> Объект читается из БД, модифицируется в памяти и сохраняется обратно.
> При конкурентных запросах происходит lost update, так как каждый запрос работает со своей копией данных.
> `transaction.atomic` не решает проблему, потому что не обеспечивает сериализацию доступа.
> Решение — использовать атомарные обновления через `F()` expressions или блокировки строк (`select_for_update`).


# 🏆 Коротко:

❌ `investor.a += 100; save()` — опасно
✅ `update(a=F('a') + 100)` — правильно
